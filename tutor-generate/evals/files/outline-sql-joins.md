# 学习大纲：SQL 表连接

## 学习者画像
- **当前水平**: 会写基本的 SELECT、WHERE、ORDER BY，能操作单表查询。没有多表操作经验。数学基础一般，不习惯集合论术语。
- **深度-广度策略**: 广度优先。先建立对各类 JOIN 的直觉理解，不深入优化器或执行计划。

---

## 模块 1：为什么需要多张表——从一张大表到分表设计
- **前置条件**: 单表查询基础（SELECT、WHERE）
- **教学方法**:
  1. **具体例子**: 一个在线书店——如果所有数据塞在一张表里：每本书的作者信息、出版社信息、订单信息全部重复存储。演示修改一个作者名字要改几百行的痛苦。
  2. **模式识别**: 电商系统（用户表+订单表+商品表）、学校系统（学生表+课程表+成绩表）——都是分表的模式。
  3. **抽象定义**: 数据规范化 = 把信息拆分到不同表中，每张表负责一类实体，通过"关联键"建立联系。关联键就是两张表共有的一个列。
- **核心要点**: 分表是为了避免数据重复，表之间通过共同的列（关联键）建立联系。
- **暂不涉及**: 数据库范式（1NF/2NF/3NF）、外键约束的创建语法。[(后续展开)]
- **过渡到下一模块**: 表拆分后，查询需要的数据分布在多张表中——我们需要把表"拼回来"。

## 模块 2：INNER JOIN——只保留能匹配上的行
- **前置条件**: 模块 1（分表设计和关联键的概念）
- **教学方法**:
  1. **具体例子**: 书店数据库——`books` 表（book_id, title, author_id）和 `authors` 表（author_id, name）。用 INNER JOIN 查出每本书及其作者名。
  2. **模式识别**: 订单+客户（查每个订单的客户名）、学生+课程（查每个学生的选课名称）——都是"两张表通过共有的列匹配"的模式。
  3. **抽象定义**: INNER JOIN = 取两张表中满足关联条件（ON）的行，不满足条件的行被丢弃。只返回交集中的行。
- **核心要点**: INNER JOIN = 只留下两表中能配对的行，配不上的就扔掉。
- **暂不涉及**: JOIN 和子查询的性能对比、多表 JOIN 的执行顺序、MySQL vs PostgreSQL 的 JOIN 实现差异。[(后续展开)]
- **过渡到下一模块**: INNER JOIN 会丢弃"单身"的行。如果书店里有一本书还没分配作者，INNER JOIN 会让它消失——这未必是好事。

## 模块 3：LEFT JOIN 和 RIGHT JOIN——保留某一侧的全部行
- **前置条件**: 模块 2（INNER JOIN）
- **教学方法**:
  1. **具体例子**: 还是书店——查出所有书，包括还没分配作者的书。LEFT JOIN `books`（左表）和 `authors`（右表），没作者的书也留下，作者列显示 NULL。
  2. **模式识别**: 报表场景（保留所有用户，即使没有订单）、数据完整性检查（找出"孤儿"记录）——都需要"保留一侧全部"的逻辑。
  3. **抽象定义**: LEFT JOIN = 左表全部保留，右表匹配上的填实际值，匹配不上的填 NULL。RIGHT JOIN 反之。
- **核心要点**: LEFT JOIN = 左表的行一个不少，右表能匹配就填，没匹配就填 NULL。
- **暂不涉及**: FULL OUTER JOIN、多条件连接的 NULL 处理陷阱、自连接（Self Join）。[(后续展开)]
- **过渡到下一模块**: 掌握了基本连接类型后，可以学习更复杂的多表查询和连接策略。
